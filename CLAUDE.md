# Daybook

Private, shared health tracker for Mark and Shelley. Hosted on GitHub Pages from `main`, root.
Live: https://learning-development667.github.io/Mark_Medical/

Named Daybook since v48 (it was Care Log until then; the repository, the Pages path and older notes below keep the old name). Strapline, on the sign-in screen and for any store listing: "Your companion between appointments." The name appears in the topbar (`setBrand()`), the sign-in and no-config screens, `manifest.json`, the Home Screen title, the PDF footer, the share title and the first line of the copied notes. The pasted-document header `=== CARE LOG DOCUMENT ===` is a data format and deliberately unchanged.

Speech to text (since v48): `speakButton(textarea)` adds a big "Tap to speak" button under a text box, using the browser's own speech recognition (`SpeechRecognition`/`webkitSpeechRecognition`: Apple's on iPhone, Google's in Chrome; nothing of ours in between, no key, no cost). Words appear in the box as recognised and can be edited like typed text; it turns warm and reads "Listening, tap to stop" while active. Wired under the Note sheet, the Question sheet, every check-in text step and the cheer board. Not rendered where the browser has no support, where the keyboard's own microphone still works.

## COST RULE (amended 2026-09-24, by Mark)
- Runs on free tiers: the Firebase Spark plan, GitHub Pages and one Cloudflare Worker on the Workers free plan (`worker/`, the "bridge"). Nothing with a monthly charge.
- Firebase: only Auth (email and password) and Cloud Firestore. No Firebase Storage, no Cloud Functions.
- Secrets never go in the public site. Anything that needs a key (the Apple Health bridge key, the Firebase service account, any future nutrition or AI key) lives in the Worker as a secret, set from GitHub repository secrets by `.github/workflows/deploy-worker.yml`. `config.js` still carries only the public Firebase web config.
- A one-off Anthropic Console credit (about $5, lasts a year) is allowed for food lookups if and when Mark decides it is worth it. Not set up yet; the app must work fully without it.
- One-off app purchases on Mark's phone (Health Auto Export lifetime, for pushing steps and sleep to the bridge) are fine.
- Document pages are stored as base64 JPEG strings in Firestore. Each page document MUST stay under 900 KB.
- History: until 2026-09-24 the rule was "Firebase and GitHub Pages only, no keys, no server". Mark relaxed it after the rule, which came from the multi-user Forge project, blocked nutrition lookups and automatic steps and sleep here.

## Branch and hosting
- All work is committed directly to `main`. No feature branches, no pull requests.
- GitHub Pages path is case-sensitive: `/Mark_Medical/`. `manifest.json` start_url and scope are `/Mark_Medical/`. `sw.js` is registered with scope `/Mark_Medical/`. All asset paths are relative.

## Standards
- Body text minimum 17px. Tap targets minimum 48px (44px is the hard floor for secondary controls). The user may be tired or drowsy: clarity beats density.
- Palette: ink #18262B, surface #FFFFFF, background #EDF1F2, accent teal #1E5F74, warm terracotta #C2703D (emphasis only), alert red #A4262C (38.0°C and above), amber #9A5B00 (37.5 to 37.9°C and waits), green #2E6B45 (done). Full dark mode via prefers-color-scheme. Never loud.
- Service worker: network-first ALWAYS. skipWaiting() on install, delete ALL caches on activate, network-first on fetch, never cache-first.
- Cache busting: `?v=VERSION` on `scripts.js` and `styles.css` in `index.html`, and the `APP_VERSION` constant in `scripts.js`. Bump on every commit.
- Run `node --check` on every JS file before committing.
- UK English throughout. No em dashes anywhere in UI copy.
- No health data in the repo, ever. Only code.
- Accessibility: WCAG 2.2 level AA, checked in v53 with axe-core (the App card under More > Settings says so, with the date) on every screen and sheet in both colour schemes (zero violations) plus hand checks for what a scanner cannot judge. Keep it that way: every sheet is a real dialog (`openSheet()` makes `.skip-link, .topbar, #main, #tabs` inert, moves focus to the title, or the first field on wide screens, and `closeSheet()` returns focus to whatever opened it; Escape closes, and `confirmSheet()` treats any close as Cancel); one keyboard focus ring for everything (`:focus-visible`, teal, never shown on tap); a skip link to `#main`; the toast is `role="status"`; the active tab carries `aria-current="page"`; `document.title` names the screen; every chart canvas gets `role="img"` and an `aria-label` built in `makeChart()` from the card's heading, the plotted range and its note; the diary donut is `aria-hidden` because its legend carries the numbers; an `aria-label` on a plain `div` or `span` needs a role (`group`, `img`); no tap target under 24px (the app's own floor is 44px) and nothing overflows at 320px wide, so the medicine purpose pill wraps, the two custom-range dates wrap, the five range buttons wrap under 360px and the calendar cells drop their 48px minimum there; in dark mode `--teal` is #5FB0C8 and `--teal-light` #142B34 (both chosen for 4.5:1), and `--teal-dark` is a button colour there, not a text colour (`.note-who`, `.speakbtn`, `.diary-macros`, `.macro-total`, `.painbtn.is-teal` switch to `--teal` in dark). AAA is not claimed: 1.4.6 enhanced contrast and 2.4.13 focus appearance are not met throughout.
- Design tokens live at the top of `styles.css` and are used everywhere; no hex values scattered through the code (the only exception is `PDF_TEAL` in `scripts.js`, because PDFs are always on white paper). Colour: `--surface`, `--surface-raised`, `--surface-sunken`, `--border-subtle`, `--text-primary/secondary/muted`, `--teal/-dark/-light`, `--warm/-dark/-light` (terracotta #C2703D, the one warm accent: attention and human warmth, used sparingly), `--success`, `--warning`, `--danger` (thresholds unchanged), `--cat-*` timeline category colours, `--sleep-deep/-core/-rem` (a single-hue ramp for the sleep chart, deepest to lightest) and `--mood-1..5` for the calendar. Elevation: `--elev-sunken`, `--elev-flat`, `--elev-raised`, `--elev-floating` (plus teal and sheet variants), all soft two-layer shadows. Radius: `--r-sm` 10 (chips, inputs), `--r-md` 16 (cards), `--r-lg` 22 (sheets, primary buttons). Spacing: `--s-1` to `--s-8` on a 4px scale. Older names (`--ink`, `--line`, `--teal-soft`, `--amber` and so on) are aliases of these, so `cssVar()` in the JS keeps working. Every text token is at least 4.5:1 on the page, a card and the sunken surface, in both colour schemes.
- Three visual levels: SUNKEN for read-only information (`.status`, the segmented track: inset shadow, a touch darker than the page, no border, never looks tappable); RAISED for anything you can tap (`.card`, `.entry`, `.qa`, `.report`, `.checkin-row`, `.docitem`, `.goal`, `.cheer`: white gradient, lit 1px top edge, two-layer shadow, press state of translateY plus reduced shadow); FLOATING for the primary action and open sheets (`.btn-primary`, `.checkin-row.is-due`, `.sheet-panel`: teal gradient, stronger shadow). Next to a primary, the partner button is outlined and lighter (`.med-actions .btn-secondary`, `.btnrow .btn-secondary`).
- Motion: screens enter with each block fading in and rising 8px, 50ms apart (`enterView()`, `.view.is-entering`); tile numbers count up via `countTo()`; timeline, cheer and document rows animate in only when new (`seenIds` sets plus `markNew()`), never on data updates; Chart.js lines draw in left to right with the area fill behind them (`drawIn()`); the tab indicator slides (`moveTabIndicator()`). All of it is off under prefers-reduced-motion.
- Charts share one style (`chartTheme()`, `lineSeries()`, `bandSeries()`, `barChart()`): gradient area fills, 2.5px rounded lines, small points with only the latest one filled and ringed, light horizontal grid only, DM Mono axis labels, temperature thresholds as soft amber and red bands, blood pressure systolic teal and diastolic warm, pain and mood on a calm scale with no red. The sleep chart is a stacked bar (Deep, Core, REM, plus a muted "Not broken down" segment for nights logged without the stage split); bar height always equals the night's logged hours asleep, the same figure as the Latest tile and the short-night flag. Awake-in-bed minutes are not part of that total and show only in the tooltip.
- Icons are inline SVG symbols in `index.html` (`icon()` in JS). No emoji anywhere: the Chemo calendar shows mood as a small dot (OK, Good, Great) or ring (Low, Rough) on the `--mood-*` teal-to-warm scale (`moodMark()`), and the legend matches. Empty states (`.empty`, `data-art`) get a muted teal line drawing from the `--art-*` masks, one line of text and the action button that already sits beside them.
- Type: Bebas Neue for screen titles, section headings and large values (section headings are small, letter-spaced and muted so they frame content), DM Sans for body and buttons, DM Mono for units, times and small uppercase labels.

## Data model (Firestore)
- `entries/{autoId}`: { day "YYYY-MM-DD", at Timestamp, type "med"|"temp"|"drink"|"food"|"weight"|"vitals"|"note"|"sleep", medId?, medName?, dose?, value? (number), heartRate? (number, bpm), systolic? (number, mmHg), diastolic? (number, mmHg), oxygen? (number, %), note?, amount? (food: "A few mouthfuls"|"About half"|"Most of it"|"All of it"), detail? (food: what went with it), deep?/rem?/core?/awake? (sleep stages, minutes), addedBy, createdAt }
  - Daily check-ins: `entries/{YYYY-MM-DD}_{morning|evening}` (deterministic id, so a day and slot can only ever have one document and reopening edits it): { type "checkin", slot, day, at, addedBy, createdAt, updatedAt, then one field per answer. Morning: sleep (1 to 10), sleepHours (number), pain, mood, symptoms (text), lookingForward (text). Evening: pain, mood, worstPain, sickness, appetite, energy, symptoms, settled, goodThing }. A skipped slider is stored as `null`, skipped text as `""`, never 0. Questions are defined in `CHECKIN_QUESTIONS`; the flow (`openCheckin`) is one question per screen with a progress bar, Back and Skip on every step, a Today/Yesterday picker on the first step, and a review screen before saving. Saving mirrors mood to `days/{day}.mood` (1 to 5, `ceil(mood/2)`) and the evening `goodThing` to `days/{day}.good`, so the Chemo calendar faces, Notes for the team and the low-mood flag keep working; the Chemo day sheet no longer edits mood or "one good thing". Home shows both slots with their state (Due now before 15:00 for morning, after for evening; Done HH:MM; Missed; Later today), and since v54 the Question for the team row sits under them in the same list, so the three align.
  - Pain readings: `entries/{autoId}` { type "pain", value 1 to 10, note? } from the Pain tile in Today's quick-add grid (`openAdd('pain')`, since v54; until then a "Log pain now" button above the grid, dropped because the check-ins already ask twice a day and the between-times reading deserved a tile, not a banner). The Trends Pain chart draws the line from check-in `pain` scores and shows these as hollow points; the Mood chart uses check-in `mood`. Notes for the team flags pain 5 to 6 amber and 7+ red (check-in or reading), worstPain 7+, sickness 6+, appetite or energy 3 and under, and lists the check-in text answers as notes.
  - Sleep entries: `value` is minutes asleep for the night before, logged against the morning (`day` is the wake-up date). Since 2026-09-24 they arrive automatically from Apple Health through the bridge as `entries/{day}_sleep` (`addedBy: "Apple Health"`, see Bridge); the Sleep sheet is for corrections and missed nights. If the selected morning already has a sleep entry the sheet opens it for editing (`editId`, `updateEntry()`) instead of adding a second one. The four stage fields (awake, rem, core, deep, in Apple's order) are always shown, and `bedAt`/`wokeAt` ("HH:MM" strings) record the night's window, with the entry's `at` set to the wake time. "Woke at" fills itself in from bedtime plus time asleep plus any awake minutes until it is typed in by hand. Shown on the Today timeline, as a Latest tile and a bar chart in Trends, in the readings line of Notes for the team, and flagged there as a short night under 5 hours.
  - Food entries: `note` is the meal name, `detail` the optional "what is in it" text. The Food diary (Trends > Reports) lists food entries day by day with each day's drinks total, over 7 to 90 days or a custom range (see Report ranges below), and has a Print button (print stylesheet in `styles.css`).
  - Calorie and macro estimates (since v42, optional): gated everywhere on `profile/main.detailedNutrition` (bool, account-wide, the toggle under More > Settings > Food, `#settings-nutrition`, `syncSettings()`). Off by default and off means nothing runs, nothing is stored and the app is exactly as it was. On, a food entry may carry `portions?: { [componentKey]: { size "S"|"M"|"L", override: null | { kcal, prot, carb, fat, per "portion"|"100g", grams } } }`, keyed per component by `macroComponentKey()` (`c:` plus the CoFID/ADDED_FOODS food code, or `u:` plus the typed phrase for something the table has nothing for). Nothing else about macros is stored; `entryMacros(index, entry)` sits beside `entryNutrition()` and recomputes on render from the same `matches` (the tag logic is untouched): grams = the component's food group's Small/Medium/Large default (`portionGroupFor()`, "typical portion, estimate", Medium by default) times `FOOD_AMOUNT_SCALE` for the entry's existing "how much" answer (0.25/0.5/0.75/1), then the row's per 100 g figures. A manual "Enter from the packet" override always wins (per portion is used as typed; per 100 g is scaled by its own `grams`); next comes a food in `profile/main.customFoods` (`[{ name, kcal, prot, carb, fat, addedBy }]` per 100 g, written by "Save to my foods" in the override panel, matched by the typed name, `customFoodByName()`; `ADDED_FOODS` in the code stays separate and curated); then the table row. A component with none of those is left out and counted ("not counted", `unmatchedChunks()` catches an unknown ingredient beside known ones, which the tag matcher would otherwise drop silently). Four render sites, all gated: the Food sheet (behind the Estimate line since v54: one row per component with S/M/L buttons showing the grams, the override panel, a totals line; a saved meal chosen there restores its own `meals/{id}.portions`), Today's timeline (`entrySub()`, "about N kcal, N g protein"; `ensureFoodIndexForToday()` fetches the table in the background and redraws once), the Food diary and its PDF/print (`diaryRow()` line per entry, `.diary-macros` per day, `dayMacros()`), and the per-day readings line of Notes for the team (`dayReadings()`, so screen, PDF and the Send/Copy text all carry it). Estimates, not medical advice, and the UI says so.
  - Editing an entry in place (since v37): food, drink, weight and note entries can be edited, not just deleted, via the same "..." entry menu (`entryOptions()`, `EDITABLE_ENTRY_TYPES`) reopening `openAdd(type, entry)` pre-filled with the entry's own values and date/time, saving with `updateEntry()` instead of creating a new one. Food diary rows (`diaryRow()`) get their own "..." menu too, so a wrong "how much" or a missing "what's in it" can be fixed from the diary itself, not just from Today's timeline; `renderFoodDiary()` re-runs after a save or delete made from there so the diary reflects the change immediately, since it fetches its own range with `loadEntriesFrom()` rather than following the live listener Today uses. Temperature, vitals, medicines, sleep, sessions and check-ins are not in `EDITABLE_ENTRY_TYPES` (sleep already has its own edit-in-place via the Sleep sheet; the others stay delete-and-re-add for now).
  - Nutrition tags (since v29): `data/cofid.json` is the official UK food table (CoFID 2021, McCance and Widdowson, Open Government Licence; 2,887 foods, per 100 g: kcal, prot, fat, sat, carb, sugar, starch, fibre (AOAC), nsp, salt unused), built and committed by `.github/workflows/build-cofid.yml` (`tools/build_cofid.py`, run by hand from the Actions tab; the gov.uk download only works from a runner). The app fetches it lazily (`loadFoodTable()`, cached in `foodIndex`) when the Food sheet or Food diary first needs it. `matchFoodText()` splits an entry's `note` plus `detail` on commas and "and/with/on", drops quantities and stop words, and looks each phrase up: the curated `FOOD_ALIASES` first (everyday words to table names, including composites such as "roast dinner", "fajitas", "full English", "homity pie"), then the table's own head words (`buildFoodIndex()`, best plain cooked form picked by `pickRepresentative()`), then two-word windows and single words, with a one-letter typo fallback for longer words. Cooking words never match on their own. `foodTags()` gives each matched food label-style tags per 100 g: Protein (10 g or 20% of energy with 5 g), Fibre (over 3 g or 1.5 g per 100 kcal), Wholegrain (starchy group plus a wholegrain word in the name), Fruit and veg (groups D and F except potatoes, juices), Dairy (group B except desserts), Starchy carbs, Good fats (nuts, oily fish, avocado, mostly unsaturated), High sugar (over 22.5 g, not fruit or veg), High fat (over 17.5 g), High sat fat (over 5 g). Small-amount groups (sauces, sugars and spreads, herbs, fats and oils) earn no tags. An entry's tags are the union of its components' tags in `FOOD_TAG_ORDER`. The diary shows the tags as chips coloured by group (`.tag.is-veg/-protein/-carb`, `NUTRI_GROUP` in the JS, since v41): Fruit and veg, Protein plus Good fats, and Fibre/Wholegrain/Starchy carbs each get their own hue (`--nutri-veg/-protein/-carb`, chosen and checked against colour-blindness with the data-viz palette validator, both colour schemes); Dairy stays a plain neutral chip and the "High ..." ones reuse the app's existing warm accent, since that is a status signal, not a fourth identity colour, kept deliberately to three so they stay tellable apart. Each day with any tags also gets a small donut chart of that day's colour mix (`donutGradient()`, a CSS conic-gradient) with a coloured-swatch legend beside it, above the existing per-day tag count line, a per-day tag count line, "Not recognised: ..." for phrases nothing matched (screen only), and an overview (`#food-overview`, days with each tag out of the days shown). The PDF has the same overview line, the same donut per day (drawn as a solid pie of triangle wedges with a white circle punched over the middle for the hole, `wedge()`/`donut()` in `buildPdfBlob()`) and a two-column table per day (`{ kind: 'table', head, rows }`) whose Nutrition cells carry the same per-tag colours, wrapped word by word (`wrapTags()`) since jsPDF has no built-in multi-colour text run. The Food sheet nudges once when a name with no detail matches nothing ("picky lunch"): a shaded box explains it will still save either way, with its own "Save without tags" button, never a silent second tap. Nothing about the tags is stored; they are recomputed on render, so improving `FOOD_ALIASES` improves every past entry. Not medical advice, and the diary says so.
  - `ADDED_FOODS` in `scripts.js` (next to `buildFoodIndex()`) holds branded products the official table was never going to have, added by hand from a photo of the product's own label, per 100 g, in the same shape as a table row (`g: null`, since CoFID's group codes don't apply). Each carries its own `aliases`, which take priority over a generic table guess for the same words. First entry: Whey protein powder, Gold Standard, strawberry (real label figures: 79 g protein, 3.3 g sugar, no fibre per 100 g; a stand-in like the table's "Build up" shake would have wrongly tagged it "High sugar"). Its generic aliases (`whey protein`, `protein powder`, `whey`) mean any whey product gets this profile until a closer match is added; close enough for whey specifically, since brands don't vary hugely, but worth another one added if a very different product turns up.
  - Questions for the team (since v45): `entries/{autoId}` { type "question", note (the question), answered (bool), addedBy, day, at } from the "Question for the team" row on Today (`#question-now`, since v54 the third row of the check-in list, same shape as the two check-ins, with a status line from `renderQuestionRow()`: "2 waiting for the next appointment, tap to add another" or "Nothing waiting, tap to add one"; `watchQuestions()` keeps `state.questions` live for it, the demo reads `recentEntries`; `openAdd('question')`, so it edits in place like a note). Shown on the timeline with a teal bar; the "..." menu offers Mark as answered / Reopen. Open questions from any date (not just the range) head the Notes for the team report, numbered, with a Mark as answered button there too; questions marked answered inside the range are counted in one muted line. `loadQuestions()` fetches them with a single `where('type', '==', 'question')` query.
  - Notes for the team (Trends > Reports), rebuilt in v45 and v46 to fit a ten-minute appointment. Four sections, on screen, in the PDF and in the Send/Copy text: (1) Questions for the team (in the PDF each has a box to tick, and "Asked by Mark, 24 Sep"); (2) Summary (`summaryRows()`): a few plain sentences, worst first, not statistics. Only topics worth checking or mentioning get a line of their own ("Pain has increased, from about 4/10 in the first half of the period to 6/10 in the second; 5 or more on 7 days, worst 8/10 on 23 Sep", "High temperature (38.0 or over) on 2 days of the 12 with a reading, peaking at 38.7 °C on 24 Sep"); a trend compares the second half of the period with the first when both halves have at least three scores (pain, sickness, appetite, energy). Amber topics that happened exactly once with no worsening trend are folded into one "One-offs worth a mention: sickness 6/10 on 25 Sep; heart rate 104 bpm on 20 Sep" line; every topic with nothing of concern shares one green line with a key figure each ("Blood pressure (116/74 to 128/82), oxygen (lowest 95%) and weight (steady at about 78.6 kg): nothing of concern"); the when-needed medicines share one teal line (amber if a daily maximum was hit). Topics: temperature, heart rate, blood pressure (the line names the reading that crossed the line, whichever number did it), oxygen, pain (check-in pain and worst pain plus pain readings), sickness, appetite, energy, sleep, weight, drinks, eating (with the food estimate per day when the Food setting is on), mood, when-needed medicines. Levels red (Check), amber (Mention), teal (Context), green (Fine), `LEVEL_WORD`/`LEVEL_RANK`, thresholds unchanged (temp 37.5/38.0, heart rate 100/120 or 50 and under, BP 140/90 and 160/100 or systolic 90 and under, oxygen 93/90 and under, pain 5/7, sickness 6, appetite and energy 3 and under, nights under 5 h, weight down 2 kg (red at 4), days under 1 L, days with nothing eaten, low-mood days); on screen as `.flag.is-*` rows with a pill, in the PDF as a `{ kind: 'flag' }` block with a coloured bar and the level word (`FLAG_RGB` in `buildPdfBlob()`); (3) Letters and documents in the range (excerpt on screen and in the PDF, full explanation in the text; `docSummary()` drops the pasted "=== CARE LOG DOCUMENT ===" header so only the explanation shows); (4) Notes: only days with written notes (`type: "note"` entries, notes attached to temp, weight, vitals, med and pain entries, and the check-in `symptoms` and `settled` answers, `REPORT_CHECKIN_KEYS`), each headed by who wrote it in bold (`.note-who`, a `{ kind: 'note' }` block in the PDF, "Mark, 10:39 (morning check-in): ..." in the text). No per-day readings, feeling or when-needed lines: the detail for any one day stays in the app. Not medical advice, and the UI says so. Letters and documents whose `docDate` falls in the range are included (title, date and full explanation in the text; a card with an excerpt and "Open the document" on screen). Send/Copy prefix the text with `NOTES_PROMPT`, asking Claude for questions for the oncologist or nurse. "Save as PDF" (`savePdf()`, jsPDF, A4, Helvetica) makes a people-facing copy without the prompt. On desktop Chrome/Edge (since v40) it opens the browser's own "Save as" dialog (`window.showSaveFilePicker()`, asked for straight away, before the PDF itself is built, so the tap still counts as a direct user gesture) so it can be saved straight to the Desktop or any folder; elsewhere it hands the file to the share sheet when files can be shared (Save to Files, Mail, AirDrop), otherwise downloads it. The Food diary has the same button. Print uses the same print stylesheet as the Food diary. A "Preview" button next to it (since v38, `previewPdf()`) opens the same PDF in a new tab to look at without sending or downloading it; the tab is opened synchronously before the PDF itself is built (`buildPdfBlob()`, the shared PDF-drawing code both `savePdf()` and `previewPdf()` call), which is what stops browsers treating the later navigation as a blocked pop-up.

(the same per-component map a food entry carries, only written when the Food setting is on), addedBy, createdAt, updatedAt, and since v54 lastAt (Timestamp), uses (count) and slots ({ breakfast, lunch, dinner, snack } counts, from the time being logged: 05 to 10, 11 to 14, 15 to 20, else snack, `mealSlot()`) }. Managed under More > Saved meals.

All are optional; at least one is required to save. Manual entry only, no HealthKit or Shortcuts integration.
- `medicines/{id}`: { name, dose, how, purpose, kind "scheduled"|"prn", perDay?, minGapHours?, maxPerDay?, courseEnd? "YYYY-MM-DD", active, order }
  - The Meds tab has its own day-nav (`#meds-day-prev/-label/-next`), sharing `state.selectedDay` with Today (since v36): the same day picked on either tab shows its own dose history on the other, rather than the Meds tab always meaning "right now". `renderMeds()`/`medCard()` take that day rather than always reading `todayStr()`, so the dose dots, "X of Y" counts, time chips and course-end pill all reflect the day being viewed; only genuinely real-time things (the PRN "Can be given now"/"Next from"/"Maximum reached" pill, and the "Log now" button, which always means this instant) are hidden when the viewed day isn't today, leaving "Log a dose" (the old "Other time", pre-filled to the viewed day) as the way to log or backfill a dose for a day other than today. A day with nothing logged reads "Not given this day" rather than showing a stale "Last ..." line from a different day.
- `documents/{autoId}`: { title, docDate, kind "images"|"text", category "general"|"chemo"|"exemption", pageCount, text?, explanation, addedBy, addedAt, updatedAt }
  - `category: "chemo"` documents are the chemo plan, listed in the Chemo tab as well as in Documents.
  - `category: "exemption"` is the NHS prescription exemption certificate, listed on the Meds tab (`meds-docs-section`, "Add exemption certificate") as well as in Documents, so it is one tap away at the pharmacy counter. Excluded from the Notes for the team report (`buildNotesReport()`), since it is not a clinical letter. `openAddDocument('exemption')` pre-fills the title with "NHS Medical Exemption Certificate".
  - Title, date and category can be changed after saving ("Edit title, date or category" on the document screen).
- `documents/{autoId}/pages/{pageNumber}`: { data base64 JPEG, width, height }
- `days/{YYYY-MM-DD}`: { chemo (bool, session planned), chemoDone (bool), mood? (1 to 5, mirrored from the check-ins), good? (string, mirrored from the evening check-in), updatedBy, updatedAt }
- `cheers/{autoId}`: { text, addedBy, createdAt } (the cheer board on the Chemo tab, newest first, last 50 shown)
- `exercise/{YYYY-MM-DD}`: { day, steps? (number), done: { pressups, situps, plank, squats } (bools), addedBy, updatedAt }
  - Steps arrive automatically from Apple Health through the bridge (`exercise/{day}.steps`, `addedBy: "Apple Health"`); the Steps sheet is for corrections. The Exercise tab has day arrows, and the Steps sheet has its own month calendar (`openStepsSheet()`, days already logged shown green, future days disabled) so any past day can be logged directly, retrospectively and in any order. Save writes the tapped day and keeps the sheet open, so several days can be logged in one sitting; switching to a different day, or leaving via Done, the round close button or the backdrop, saves whatever is typed and not yet saved first (`saveIfDirty()`, and the generic `openSheet(title, body, onClose)` close-guard it uses), so nothing typed is ever silently dropped.
- `nutrition/{YYYY-MM-DD}` (since v51): { day, kcal, prot, carb, fat, source "apple-health"|"manual", addedBy, updatedAt }. The day's food totals from whatever app the person logs food in. Arrive automatically through the bridge from Apple Health (Health Auto Export metrics Dietary Energy, Protein, Carbohydrates, Total Fat, summed per day; MyFitnessPal, Nutracheck and Apple's own app all write to Health), or typed in from the Food diary's "Day totals from your food app" button (`#food-totals`, for Android or anyone without the feed; family only, hidden read-only). `watchNutrition()` keeps `state.nutrition`; `loggedTotals(day)` returns a day's totals or null. Where a day has them they replace the app's own estimate: the Food diary day line reads "From Apple Health ..." or "From your food app ..." instead of "Estimate ..." (shown even with the estimates setting off, since they are logged figures, not estimates), and the Notes summary's Eating line averages them, saying where they came from. The protein target comparison uses whichever figure applies.
- `profile/main`: { calls: [{label, number}], exerciseGoals?: { pressups, situps, plankSeconds, squats }, detailedNutrition? (bool, the Food setting), customFoods? (see Calorie and macro estimates), proteinTarget? (number, grams a day, from the dietitian, More > Settings > Food, since v50) } (goal defaults 20, 20, 60, 2; editable in the app)
  - Protein (since v50, asked for by the dietitian): every estimate line carries the meal's or day's protein share of energy ("12 g protein, 24% of energy", `fmtMacroLine()`), and when `proteinTarget` is set each Food diary day says "protein target 100 g met" or "protein 12 g under the 100 g target" (`proteinTargetText()`), and the Notes summary's Eating line reads "... against the 100 g protein target, under on 5 of 7 days" (amber when under on more than half the days).

## Bridge (Cloudflare Worker, `worker/`)
- Deployed as `care-log-bridge` on workers.dev by `.github/workflows/deploy-worker.yml` whenever `worker/**` changes on `main` (or by hand from the Actions tab). The job stops early with a notice, not a failure, until the four repository secrets exist: `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `BRIDGE_KEY`, `FIREBASE_SERVICE_ACCOUNT`.
- Writes to Firestore through the REST API with the Firebase service account (JWT signed with WebCrypto, token cached for the hour). A service account bypasses `firestore.rules`, so nothing in the rules changes for it.
- `POST /health`: the inbox for the Health Auto Export app (iOS, Premium/lifetime, background REST automation). Auth is the `X-Care-Log-Key` header matching `BRIDGE_KEY`. Metric `step_count` rows are summed per day into `exercise/{day}.steps` (merge, `addedBy: "Apple Health"`). Metric `sleep_analysis` rows become `entries/{day}_sleep` (deterministic id, `day` is the morning the sleep ended, `value` minutes asleep, `core`/`deep`/`rem`/`awake` minutes, `bedAt`/`wokeAt` "HH:MM" from the sleep start and end, `at` the sleep end, `addedBy: "Apple Health"`, `source: "health-auto-export"`), so re-sends update the same document. The last raw payload is kept at `bridge/last` (trimmed to 20 KB) to check the exact field names after the first real send; the parser reads the sleep fields leniently (`asleep`/`totalSleep`, `sleepStart`/`inBedStart`, `sleepEnd`/`inBedEnd`).
- `GET /ping` is a health check. CORS is allowed only for the GitHub Pages origin, for the app's own future calls (nutrition lookups).
- Planned next on the bridge: `GET /food?barcode=` proxying Open Food Facts (keyless, 10 requests a minute, no CORS of its own), cached in a `foods` collection.

## Report ranges (since v42)
Notes for the team and the Food diary share one range control (`wireReportRange()`, `reportRange()`, `reportRangeLabel()`): the 7/14/30/90 day presets plus Custom, which shows two native date inputs (`#food-custom-from/-to`, `#notes-custom-from/-to`; To defaults to today, From to 14 days earlier, both capped at today). To may not be before From, and the range is capped at `CUSTOM_RANGE_MAX_DAYS` (180) with a short inline message (`.hint-warn`) that leaves the previous range showing. The header reads "From 21 Sep 2026 to 3 Oct 2026" for a custom range and keeps "Last 14 days, from ..." for presets; the PDF, print and the Send/Copy text use the same `from`/`to` (both inclusive; entries are fetched from `from` and filtered to `<= to`, `buildNotesReport(entries, from, to)`, `vitalsFlags(entries, from, to)`), and the Send/Copy text states the range in its first line. The last custom range lives in `state` (`foodRangeMode`, `foodCustomFrom/To`, the same for `notes`) for the session only, never in Firestore. Reason: appointments do not fall on neat 7 or 14 day boundaries.

## Navigation
Six bottom tabs: Today, Meds, Trends, Chemo, Exercise, More. The topbar names the page (`setBrand()`, `PAGE_TITLES`, since v43): "Care Log: Today", "Care Log: Medicines", "Care Log: Trends", "Care Log: Chemo plan", "Care Log: Food diary" and so on, with the page part lighter and smaller (`.brand-page`), so the report pages and the Chemo tab carry no heading of their own. The Chemo tab is called "Chemo plan" (it was "Chemo Party Plan" until v43; renamed with a wider audience in mind). More is a short menu of rows (`.menu`, reusing the `.checkin-row` look): Letters, results and paperwork; Saved meals; Settings (its own view, `view-settings`, Back returns to More, highlights the More tab) with the Food toggle and the App card; then Who to call stays inline, since phone numbers should be one tap away, and Sign out. "Vitals" is the name of the reading you log (the Today quick-add button and the Log vitals button); "Trends" is the look-back tab: a Reports row (Notes for the team, Food diary, Documents), the Latest tiles and every chart. The tab's internal ids stay `vitals` (`view-vitals`, `data-tab="vitals"`). Documents also lives under More (chemo plan documents under Chemo, and the exemption certificate under Meds); Saved meals, who to call and the app section are under More. Report pages remember the tab they were opened from (`state.reportReturn`, `state.docsReturn`) for Back and for tab highlighting.

## Access
Accounts are data, not code (since v44). Each sign-in (created under Authentication > Users in the Firebase console) has a document `users/{uid}`: { name, role "family"|"readonly"|"viewer", relation? "patient"|"carer"|"" }, also created in the console, never by the app. `firestore.rules` gates every collection on that record (`hasRole()`, which reads `users/{uid}`; a signed-in person can read only their own record, nobody can write one), and the app reads it at sign-in (`loadAccount()`, `state.account`). No email address appears in the rules, in `config.js` or anywhere on the site; the repository is public, so that matters. Since v49 there is no fallback: a sign-in with no `users` record is refused with "This account is not set up for Daybook yet." Since v52 that refusal happens only when the server itself answers that there is no record (`loadAccount()` returns `{ missing: true }`); a read that fails or times out (weak signal, the phone waking the app) returns `{ error: true }` after three retries and the person stays signed in, with a "Could not reach Daybook to check your account" message and the Sign in button re-running the check (`enterApp()`, which the auth listener also calls). The last good record is cached on the phone (`localStorage`, `daybook.account.{uid}`) so a weak signal at start-up opens the app at once. Before v52 any error signed the person out, and because `stopData()` did not clear `state.recentFrom`, signing straight back in left `watchRecent()` skipped and every new entry from either phone invisible until a full reload; `stopData()` now resets `recentFrom`, `recentEntries` and `dayEntries`. Two family accounts (Mark, the patient, and Shelley, the carer) have full access. Sign-in screen only; no sign-up flow.

Rolling the change out without locking anyone out, in this order: (1) with the old rules still live, create the three `users` documents, either in the console (uid from Authentication > Users) or, easier, from the Actions tab: "Seed a user record" (`.github/workflows/seed-user.yml`, `tools/seed_user.mjs`) takes uid, name, role and relation as a form and writes `users/{uid}` with the bridge's `FIREBASE_SERVICE_ACCOUNT` secret, so nothing leaves GitHub and no console dialog is involved; run it once per person, re-runs update in place; (2) publish the new `firestore.rules`; (3) sign out and in on one phone to confirm; (4) drop the `users` map from `config.js`.

### Full read-only access (since v35)
Hayley's account sees everything a family member sees: all six tabs, every report (Notes for the team, Food diary, Documents), every chart, every document, exactly like Mark or Shelley, but cannot create, edit or delete anything anywhere. This is deliberately different from the narrower "viewer" role below, added after that narrower slice turned out not to be enough. Set up by giving their `users/{uid}` document `role: "readonly"`; the rules grant read on every collection (`entries` of every type, `medicines`, `documents` and its `pages`, `profile`, `days`, `cheers`, `exercise`, `meals`) and write stays `isFamily()`-only on all of them, enforced at the database level.
Signing in as read-only (`state.account.role === "readonly"`, `state.readOnly`) sets `setReadOnlyMode(true)`: a "Read only" pill shows in the topbar (`#readonly-pill`); the bottom nav and landing tab are untouched (all six tabs, lands on Today like anyone else); `startData()` still skips `seedMedicinesIfEmpty()` (a write) but otherwise loads every collection exactly as for a family member. Every add/edit/delete control is hidden throughout the app (`body.is-readonly` in `styles.css`, targeting `.qa`, `#pain-now`, `#meds-manage`, `.med-actions`, `#meds-doc-add`, `#vitals-log`, `.cheer-add`, `#chemo-doc-add`, `#ex-steps-edit`, `#ex-goals-edit`, `#doc-add`, `#doc-edit`, `#doc-paste-summary`, `#doc-save-explanation`, `#doc-delete`, `#more-meals`, `#calls-edit`), while the underlying information stays visible: dose-time chips and the timeline's "..." entry menu render as plain non-interactive text/nothing instead of a button (mirroring the existing `state.viewer` pattern), the exercise goal buttons and Today's check-in rows are disabled in place rather than hidden so their status text stays readable, the document explanation textarea is set `readOnly` rather than removed, and the chemo calendar's day cells stay tappable but `openDaySheet()` renders a plain-text summary (chemo status, mood, "one good thing") with a Close button instead of the checkboxes and Save/Remove buttons a family member gets.

### Narrow read-only viewer
A further account can be added for someone who should see only Mark's medicines, the chemo plan and mood, and the Trends charts, with nothing else visible at all (not even Today, Exercise, More or the reports). Set up by giving their `users/{uid}` document `role: "viewer"` (none exist today). The rules grant read-only access on `medicines`, `days` (chemo/mood) and `entries` of type `med`, `temp`, `vitals`, `weight`, `sleep` or `drink` only; `food` and `note` entries, `documents`, `cheers`, `exercise`, `profile` and `meals` stay `isFamily()`-only, so this is enforced at the database level, not just hidden in the UI.
Signing in as a viewer (`state.account.role === "viewer"`, `state.viewer`) sets `setViewerMode(true)`: the bottom nav drops to three tabs (Meds, Chemo, Trends), landing on Meds; a "View only" pill shows in the topbar; and every add/edit/delete control on those three tabs is hidden (Log now/Other time/Manage medicines, the Meds tab exemption certificate section, Log vitals, the Reports row, the Chemo cheer board and plan documents section, and the calendar days stop being tappable). Today, Exercise, More and the reports are never reachable by a viewer.

## Guest preview mode
A "Guest" button on the sign-in screen gives a fully interactive preview of the app with made-up example data, no Firebase account, no sign-in, no Firestore access at all: nothing to create in the console, nothing to hand out. Tapping it sets `state.demo = true` and calls `startDemoData()`, which fills `state` from `buildDemoFixture()` (realistic made-up entries, a chemo calendar, cheer notes, exercise history). Every quick add, edit and delete throughout the file branches on `state.demo` to mutate that in-memory state and re-render, instead of calling Firestore, so the whole app is explorable but nothing is ever written anywhere; it is gone on refresh or on "Leave preview". A `Preview` pill shows in the topbar throughout. Because this path never touches `auth` or `db`, there is nothing to add to `firestore.rules` for it, and no risk of it ever reaching real data.
